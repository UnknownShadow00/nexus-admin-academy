## 1. What is this?

A fix is complete only when the original problem no longer occurs, related
functions remain healthy, the user can work, and the ticket records evidence.

## 2. Why does an IT worker care?

Closing on “looks good” creates repeat incidents and weak handoffs.

## 3. Watch / read

- Microsoft troubleshooting documentation plus the organisation's ticket standard. *(required)*

## 4. What you need to remember

- Use the least disruptive supported fix with approval and rollback.
- Repeat the exact failed action under comparable conditions.
- Check adjacent functionality and monitoring/log evidence.
- Record symptom, scope, evidence, root cause/theory, action, verification, and follow-up.
- If not proven, say what remains uncertain and escalate with evidence.

## 5. Real workplace example

Disabling one approved high-impact startup item is followed by a reboot, timed
sign-in, normal application launch, and user confirmation.

## 6. Commands / tools

Ticket template, before/after measurements, Reliability Monitor, Task Manager,
and the user's original application/workflow.

## 7. Interview / example

**How do you prove a slow-PC fix?** Repeat the measured workload, compare the
bottleneck and elapsed time, confirm expected apps work, and document the result.
